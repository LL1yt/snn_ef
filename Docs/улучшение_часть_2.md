Problem statement
Текущий тренинг-цикл делал GPU→CPU readback на каждом шаге симуляции из-за stepWithEvents, что доминировало по времени при больших stepsPerEpoch и числе частиц. Дополнительно были лишняя трассировка/аллокации даже когда UI-логи не нужны, пересоздание Metal-контекста в eval, и несколько CPU-узких мест (датасет, нормализация таргетов, IO чекпоинтов).
Current state (key hot spots)
FlowLearningLoop.runEpoch всегда шел через router.stepWithEvents в цикле stepsPerEpoch, собирая события и трейс-структуры. Sources/EnergeticCore/FlowLearningLoop.swift.
FlowMetalContext.step на каждом шаге:
копировал CPU-массивы в MTLBuffer,
делал dispatch + waitUntilCompleted(),
читал обратно массивы,
(опционально) строил events,
компактифицировал alive-частицы на CPU. Sources/EnergeticCore/FlowMetalContext.swift.
Eval создавал новый FlowLearningLoop (а значит новый FlowRouter/FlowMetalContext) на каждую оценку. Sources/EnergeticCLI/EnergeticCLIApp.swift.
LogiQADatasetLoader.loadJSONL читал весь JSONL файл целиком в память. Sources/EnergeticCore/LogiQADataset.swift.

Progress update (what is already done)
1. Fast/Slow path в FlowLearningLoop:
Slow path (stepWithEvents + трассы) включается только когда реально нужен UI payload.
Fast path использует один GPU-run на эпоху.
2. Новый GPU API: FlowRouter.simulateWithCompletions(...):
Один command buffer на эпоху, без per-step readback.
Опциональные readback'и:
includeCompletions: можно отключить GPU→CPU completions.
includeHistogram: можно отключить накопление/редукцию/чтение bins.
3. Производительность GPU:
Можно отключить запись completion record buffers на GPU (recordCompletions=0) когда readback не нужен.
Можно отключить накопление histogram на GPU (recordHistogram=0).
4. GPU weighted yHat (CompletionAggregator equivalent):
GPU считает sumWE/sumW per bin и финализирует yHat на GPU.
5. GPU scalar metrics:
meanRadialMiss и boundaryLoss считаются на GPU и возвращаются как скаляры.
6. CPU оптимизации вокруг данных:
Streaming JSONL loader.
Кэш нормализованных targetsNorm и wrongTargetsNorm в CLI.
Снижение издержек IO чекпоинтов (JSONEncoder без prettyPrinted).
7. Следующий крупный шаг уже сделан: GPU learning finalize (loss + gains update):
GPU считает binLoss/negativeLoss/histogramMatchL1/yHatStats/nonzeroBins (+ optionAccuracy где применимо).
Опционально GPU обновляет gains in-place и возвращает gainDeltaMean/Variance.
В fast headless training это позволяет не читать back weightedYHat каждый epoch.
Gains становятся GPU-authoritative между эпохами; CPU синхронизирует gains только по необходимости (например getParameters/slow UI epoch).

Proposed changes (overview)

1. Разделить режимы обучения: fast path без пер-step событий/трейсов и slow path для редкой UI-диагностики.
2. Переиспользовать один eval-loop вместо пересоздания Metal контекста.
3. Реализовать “правильный” simulateWithCompletions: один GPU-run на эпоху без per-step readback, который возвращает:
   гистограмму yHat (bins),
   completion-записи (bin/pos/energy/spiked + initialBin для align),
   spikeCount/stepCount (для spikeRate),
   completionCount (для completionRate).
4. CPU-оптимизации вокруг данных: streaming JSONL, кэш нормализованных таргетов/негативов, убрать словари там где id плотные.
5. Снизить издержки IO для чекпоинтов/summary (опционально).

   A. Fast/Slow path в FlowLearningLoop
   Цель: когда UI-лог не нужен, не собирать events, traceSteps, pathPoints, и не делать шаговую синхронизацию.
   В FlowLearningLoop.runEpoch ( Sources/EnergeticCore/FlowLearningLoop.swift ) ввести выбор режима:

   например emitLog && (epoch % max(1, learningConfig.logEveryUI) == 0).

   В fast path:
   CompletionAggregator.aggregate остается CPU (как сейчас), но входные CompletionEvent строятся из буферов completions.
   boundaryLoss и meanRadialMiss считаются из completion позиций, без step-by-step.

    D. Bins участвуют в обучении: “вариант 2” (GPU weighted yHat)
    Цель: сделать так, чтобы обучение могло использовать сигнал, вычисленный напрямую "в бинах" на GPU, сохранив идею умных весов (wDist/wEnergy/wAlign). Это снижает CPU-нагрузку и делает bins частью training objective.
    Ключевая мысль: здесь bins становятся не "сырой суммой", а именно yHatWeighted[b] = sum(w*E_adj)/sum(w) на GPU, то есть эквивалентом CompletionAggregator.
    D1. Формула и источники данных
    Для каждого completion (boundary-crossing) в bin b:
    E_adj = max(0, energy) * gain[b]
    wDist = exp(-|r - R| / sigmaR)
    wEnergy = exp(-|E_adj - targetRaw[b]| / sigmaE) (если targets предоставлены и длина == bins, иначе fallback по maxE)
    wAlign = exp(-angularDistance(initialBin, b) / tau) (если initialBin != -1, иначе 1)
    w = (wDist^alpha) _ (wEnergy^beta) _ (wAlign^gamma)
    Агрегация по bin:
    sumWE[b] += w * E_adj
    sumW[b] += w
    В конце:
    yHatWeighted[b] = sumWE[b] / max(sumW[b], eps)
