# Проблема
Нужно реализовать улучшения с приоритетом «простое, но даёт большой выигрыш», с упором на GPU/Metal и без CPU‑фолбэков.

# План реализации (фазы, простое → сложное)
## Фаза 0: быстрые исправления и согласование конфигурации
0.1. Реализовать `seedLayout` (`ring`/`disk`) в `FlowSeeds` с детерминированной формулой (угол + радиус), пригодной для GPU.  
Источник: `Sources/EnergeticCore/FlowSeeds.swift (1-75)`, `Docs/config_center_schema.md (130-210)`.

0.2. Ввести «финальную проекцию» для оставшихся частиц с весом по близости к границе.  
Идея: при `t == T` добавлять вклад `E * w`, где `w = clamp(r/R, 0..1)^p`.  
Параметр `p` — `flow.projection.final_weight_power` (default 1.0, диапазон > 0).  
Источник: `Sources/EnergeticCore/FlowRouter.swift (140-175)`, `Docs/config_center_schema.md (130-210)`.

0.3. Сделать `LoggingHub.emit(process:)` fail‑fast при неизвестном alias, с явным пояснением, что нужно добавить alias в `process_registry` или использовать канонический id. Добавить alias `capsule.decode`.  
Источник: `Sources/SharedInfrastructure/LoggingHub.swift (40-80)`, `Sources/SharedInfrastructure/ProcessRegistry.swift (1-70)`, `Sources/CapsuleCore/CapsuleCodec.swift (1-70)`.

0.4. Убрать `try!` в `EnergeticCLI` и заменить на `Diagnostics.fail`.  
Источник: `Sources/EnergeticCLI/EnergeticCLIApp.swift (1-140)`, `Sources/SharedInfrastructure/Diagnostics.swift (1-80)`.

0.5. Защитить NaN‑сценарии при пустых энергиях в `FlowLearningLoop`.  
Источник: `Sources/EnergeticCore/FlowLearningLoop.swift (1-220)`.

## Фаза 1: GPU‑готовый формат данных и детерминизм
1.1. Перейти на SoA‑формат в `FlowState` (posX/posY/velX/velY/energy/V/id) и сделать in‑place компакцию без аллокаций на шаг.  
Источник: `Sources/EnergeticCore/FlowTypes.swift (1-90)`, `Sources/EnergeticCore/FlowRouter.swift (1-175)`.

1.2. Унифицировать `step` и `stepWithEvents` в один вычислительный путь.  
Источник: `Sources/EnergeticCore/FlowRouter.swift (1-175)`.

1.3. Заменить RNG на counter‑based вариант (ключ `(particleID, step)`), чтобы детерминизм совпадал с GPU.  
Источник: `Sources/EnergeticCore/FlowTypes.swift (35-70)`.

## Фаза 2: Metal‑реализация (GPU без фолбэков)
2.1. Описать layout `MTLBuffer` под SoA и создать Metal‑pipeline для `FlowRouter`.

2.2. Реализовать два compute‑kernel: `FlowStepKernel` (LIF/скорость/позиция/энергия) и `FlowProjectKernel` (проекция + histogram). Гистограмма — глобальные атомики.

2.3. В `FlowRouter` переключиться на GPU‑путь без runtime‑фолбэков на CPU. CPU‑код может остаться reference‑only, но не используется в проде.  
Источник: `Sources/EnergeticCore/FlowRouter.swift (1-175)`, `Sources/EnergeticCore/FlowProjector.swift (1-45)`.

## Фаза 3: Интеграция, конфиг и наблюдаемость
3.1. Расширить ConfigCenter: добавить `flow.projection.final_weight_power` и (если нужно) `flow.compute_backend` со значением `metal`.

3.2. Обновить документацию схемы конфига.

3.3. Добавить signpost‑метрики для GPU‑шагов (`step`, `project`) через `LoggingHub`.  
Источник: `Docs/config_center_schema.md (130-210)`, `Sources/SharedInfrastructure/LoggingHub.swift (1-170)`.

## Фаза 4: Профилирование и целевые оптимизации под M4
4.1. Подбор размеров threadgroup, минимизация атомиков при типичных размерах B и N.

4.2. Проверка загрузки GPU/Unified Memory, устранение лишних копий.

4.3. Обновление snapshot/метрик для UI и headless режима.

# Принятые решения
A) Финальная проекция: применяем для всех оставшихся частиц с весом по близости к границе. Вес линейный или степенной `w = clamp(r/R)^p`, параметр `p` конфигурируемый.  
B) LoggingHub: fail‑fast при неизвестном alias с явным сообщением «добавьте alias в process_registry». Добавляем `capsule.decode`.  
C) GPU‑гистограмма: используем атомики в глобальный histogram.  
D) CPU/GPU сравнения не делаем, так как GPU‑путь без фолбэков.

# Тесты и верификация (без CPU/GPU сравнений)
Фаза 0: тесты на `seedLayout` (ring/disk), финальную проекцию (монотонность веса), корректный fail‑fast для неизвестного alias, обработка ошибок в CLI, защита от NaN в обучении.  
Фаза 1: тесты детерминизма RNG и корректности in‑place компакции (число частиц, отсутствие NaN/Inf).  
Фаза 2: GPU‑smoke тесты на малых сценах (детерминизм при фиксированном seed, длина bins, неотрицательность энергии, корректность финальной проекции). При необходимости — golden‑векторы, но без сравнения с CPU.  
Фаза 3: интеграционные тесты headless CLI и snapshot‑формата.

# Риски
- Детерминизм GPU и точность atomics могут влиять на воспроизводимость метрик.
- Семантика финальной проекции изменяет распределения по бинам и динамику обучения.
- Переход на SoA и in‑place компакцию требует строгой синхронизации индексов.
